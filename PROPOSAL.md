# TypedFlake redesign proposal

**Status:** Draft — public syntax refined; implementation has not started.

This document describes the intended design, not the current implementation.
All Rust examples describe the target interface, not currently available features.
Accepted choices and remaining implementation decisions are recorded below.

### How to read this document

This design is the plan: implement it as described. It is the default for every
decision it covers, and it is not a menu of suggestions.

It is also not a cage. Code snippets, signatures, names, error payloads, limits,
and narrowly specified cases were written before any implementation existed. If
real code reveals a clear improvement over one of them, take the improvement
instead of holding to the text.

- **Follow the design by default.** Do not deviate out of preference or
  convenience alone.
- **Improve when there is a concrete reason:** something simpler, more idiomatic,
  more correct, or a problem the text did not foresee.
- **Record every deviation here** with a short reason, updating the affected
  example and decision row, so the document keeps matching the code.
- **Goals and guarantees are not up for improvement this way.** If one of them
  cannot be met, discuss it before working around it.

## 1. Goals and scope

### Agreed goals

- Make declaring and generating IDs for distinct domain identities easy.
- Preserve the convenient `UserId::generate()?` entry point.
- Support both `i64` and `u64` newtypes.
- Allow lower-capacity formats without requiring every storage bit to be used.
- Share readable format constants across identity types.
- Support a simple node number or a custom split with named fields.
- Integrate naturally with Serde, SQLx, and `tokio-postgres`.
- Keep integration derives separate from ID format attributes.
- Keep generation efficient and implementation details private.
- Prefer correct, idiomatic Rust contracts over backward compatibility.
- Refine the design incrementally before implementing it.

### Non-goals

- Assigning distributed node IDs, managing leases, or coordinating deployments.
- Proving that a parsed ID was generated by this library or exists in a database.
- Providing arithmetic on IDs or implicit conversions between identity types.
- Building a general-purpose bitfield framework.
- Supporting every database, runtime, clock policy, or integer width initially.

The guiding principle is a small interface that hides the complexity of generation,
representation, and integration without hiding operational responsibilities.
Keep documentation focused on conventional Snowflake layouts. Explain reduced
capacity as a supported capability, not through a catalog of unusual bit layouts.

## 2. Proposed public interface

### Declare identities and generate IDs

```rust
use typedflake::typedflake;

#[typedflake(epoch = "2025-01-01")]
pub struct UserId(i64);

#[typedflake(epoch = "2025-01-01")]
pub struct OrderId(i64);

// Once, during application startup.
typedflake::init(17)?;

// Anywhere in the application.
let user_id = UserId::generate()?;
let order_id = OrderId::generate()?;
```

`UserId` and `OrderId` are distinct nominal types, not aliases for integers.

The attribute macro owns the standard ID behavior: `Debug`, `Clone`,
`Copy`, equality, ordering, hashing, `Display`, `FromStr`, numeric conversions,
and `repr(transparent)`. It does not provide `Deref`, arithmetic, or `Default`.
Duplicate implementations of owned traits must produce clear diagnostics;
unrelated user derives remain possible.

This replaces the current derive-based declaration. Initially accept only
non-generic tuple structs with one private `i64` or `u64` field. Reject unsupported
shapes, conflicting representation attributes, and duplicate owned traits clearly.
Do not add integration implementations implicitly.

`#[typedflake(...)]` must be the first attribute on the struct, above any
`#[derive]`. An attribute macro only sees the attributes below it, so this order
is what lets it diagnose duplicate owned traits. `Debug` prints `UserId(123456789)`;
`Display` prints the plain decimal value.

### Configure the persistent format

```rust
use typedflake::{BitLayout, Epoch, Format};

pub const APP_IDS: Format = Format {
    epoch: Epoch::from_date(2025, 1, 1),
    bits: BitLayout {
        timestamp: 41,
        node: 10,
        sequence: 12,
    },
};

#[typedflake(format = APP_IDS)]
pub struct UserId(i64);

#[typedflake(format = APP_IDS)]
pub struct OrderId(i64);
```

Use normal Rust struct literals with named fields, not positional constructors,
builders, or another configuration macro. `Format` groups epoch and layout;
`BitLayout` groups only the bit allocation. Both are copyable declarative
specifications. A `BitLayout` constant can also be reused by several formats.

The public attribute is named `format`, not `config`: it describes persisted data,
not deployment or waiting behavior. The referenced expression must be a constant
`Format`. The generated declaration validates it in a const context against the
ID representation and node schema. Invalid specifications cannot become usable ID
formats merely by being declared as public struct literals.

For local declarations, the equivalent inline syntax is:

```rust
#[typedflake(
    epoch = "2025-01-01",
    bits(timestamp = 41, node = 10, sequence = 12),
)]
pub struct UserId(i64);
```

Attribute grammar follows Rust conventions: scalar options use `name = value`,
and related options use `group(name = value, ...)`. Use `epoch = ...` and
`bits(...)`, not `bits = (...)`, positional numbers, or struct-literal colons
inside attributes. Require commas and allow trailing commas.

Rules:

- Supply either `format = CONSTANT` or an inline `epoch`; epoch is required.
- Do not combine `format` with inline epoch or bit overrides.
- The inline epoch accepts only `"YYYY-MM-DD"`, meaning midnight UTC. Any other
  instant uses a `Format` constant with `Epoch::new(unix_millis)`.
- The time unit is always milliseconds.
- Epoch validation is calendar-only and const. It never reads the clock: an epoch
  in the future or too old for the timestamp width surfaces at generation as
  clock-before-epoch or timestamp exhaustion.
- Omitting `bits` selects 10 node bits, 12 sequence bits, and the remaining usable
  width for timestamp: 41 bits for `i64`, 42 for `u64`.
- An explicit `bits(...)` group supplies all three fields. Do not infer missing
  fields or change a shared format depending on its consumer.
- Timestamp and sequence widths must be greater than zero. Node width may be zero,
  in which case only node zero is valid.
- Sum the widths using checked/widened arithmetic. The total must be at most 63
  for `i64` and at most 64 for `u64`, not necessarily equal to that capacity.
- Pack sequence in the least significant bits, then node, then timestamp. Unused
  upper bits are reserved and must be zero.

Format belongs to the ID type and is immutable. Deployment configuration only
selects a node; it cannot override epoch or bit allocation globally.

### Reduced capacity

Explicit widths may use less than the storage capacity. This lowers the maximum
numeric value and potentially its decimal length, at the cost of timestamp
horizon, node count, or generation capacity. It does not provide fixed-length
decimal strings or shrink an `i64`/`BIGINT` below eight bytes.

Keep reduced-width examples in focused validation tests rather than complicating
the primary usage guide. Raw conversion and every integration decoder must reject
nonzero reserved bits. No public operation silently truncates them.

### Choose a representation

| Representation | Default-format raw values | Default timestamp bits | Approximate horizon |
| --- | --- | --- | --- |
| `i64` | `0..=i64::MAX` | 41 | 69.7 years |
| `u64` | `0..=u64::MAX` | 42 | 139.4 years |

Recommend `i64` for portable signed database storage. Reserve its sign bit and
reject negative inputs. Zero is structurally valid. Never reinterpret a full-width
`u64` as a negative `i64` to make it fit a database column.
For reduced-capacity formats, the accepted range is further limited by the
configured used bits.

```rust
let raw: i64 = user_id.get();
let restored = UserId::try_from(raw)?;
let raw: i64 = user_id.into();
let parsed: UserId = "123456789".parse()?;
let text = user_id.to_string();
```

Use a uniform `TryFrom<i64>` and `TryFrom<u64>` input interface for every ID,
checking sign, representation capacity, and reserved bits. A full-width unsigned
format accepts every `u64`, but does not get a different constructor trait from a
reduced format. Do not also implement `From<raw>`: its blanket `TryFrom` would
conflict with the explicit checked conversion.

Output to the declared underlying integer uses infallible `From<Id>`. Cross-width
or signedness changes beyond those ID input conversions can use the primitive
integer's checked conversions; do not add aliases for every combination.
`get()` returns the declared underlying integer without initialization or allocation.

### Use a simple or structured node

Simple deployment:

```rust
typedflake::init(17)?;
```

The simple node is a plain `u32`, not a wrapper type. Its valid range depends on
each ID's format, so a newtype could not carry an invariant. Like a typed node,
it is input validated when consumed. `u32` is the only integer that acts as a
node; this is what lets `init(17)` infer its type, so do not add other integer
node types later.

Structured deployment:

```rust
use typedflake::TypedNode;

#[derive(Debug, Clone, Copy, TypedNode)]
pub struct AppNode {
    #[node(bits = 5)]
    pub worker: u8,
    #[node(bits = 5)]
    pub process: u8,
}

#[typedflake(format = APP_IDS, node = AppNode)]
pub struct UserId(i64);

typedflake::init(AppNode {
    worker: 17,
    process: 1,
})?;
```

Fields pack in declaration order, most significant first. This example consumes
10 bits: `[worker: 5][process: 5]`. Field names are user-defined, not special
runtime concepts. The structure interprets the node field; it does not override
its size. Validate `AppNode::BITS == APP_IDS.bits.node` at compile time.
The same equality applies when the format is inline or uses default widths.

Use normal named struct fields instead of generating builders. A node structure
is input configuration: constructing it does not establish validity. Initialization
and generator creation validate every field before packing, without truncation.
The derive validates field widths and the aggregate layout statically.

`TypedNode` accepts only non-generic structs with named fields of type `u8`,
`u16`, or `u32`, and at least one field. Every field requires `#[node(bits = N)]`
with `1 <= N <=` the width of its type. The node type must be `Copy`.

Global defaults retain node schema identity, not just packed bits. A type expecting
one schema must not silently consume another schema with the same width. Multiple
schemas in one process can initially use explicit generators instead of a more
complex global registry of defaults.
Explicit generators for a structured-node ID accept that declared node type, not
an arbitrary packed integer. Simple-node IDs accept a `u32` node. Defer a raw
escape hatch for structured nodes until there is a concrete use case.

### Obtain an explicit generator when needed

```rust
let generator = UserId::generator(AppNode {
    worker: 17,
    process: 1,
})?;

let id = generator.generate()?;
let shared = generator.clone();
```

The return type is `Generator<UserId>`, not a generated `UserIdGenerator` type.
For simple-node IDs, the equivalent is `UserId::generator(17)?`.

Explicit generators do not require global initialization. Repeated construction
for the same ID type and node shares state, as does cloning. The static generation
path uses that same state when its default node matches. No public constructor
creates an independent, uncoordinated state for the same identity and node.

Default node matching uses in-process schema identity, not bit width alone. Simple
numeric defaults form a separate schema from custom node structures. This does
not claim to validate schema compatibility between separate processes.

### Inspect and reconstruct values

```rust
let parts = user_id.parts();
println!("{}", parts.elapsed_millis);
println!("{}", parts.node.worker);
println!("{}", parts.sequence);

let restored = UserId::from_parts(parts)?;
let unix_millis = user_id.unix_millis()?;
```

```rust
pub struct Parts<N> {
    pub elapsed_millis: u64,
    pub node: N,
    pub sequence: u64,
}
```

Simple nodes use `u32`, so `Parts<u32>` is built and read without ceremony; split
nodes use their declared structure. `elapsed_millis` is explicitly relative to the epoch.
Absolute timestamp conversion checks addition overflow.

Parsing, conversion, decomposition, and reconstruction are pure. They do not
initialize globals, create generators, or inspect the current clock. `from_parts`
checks bounds but does not reserve a sequence or guarantee uniqueness.

### Public method contract

For each ID, expose the following methods and traits. `Repr` and `Node` below
stand for that ID's declared integer and node type, not additional caller inputs.

| Entry point | Result | Contract |
| --- | --- | --- |
| `typedflake::init(node)` | `Result<(), InitError>` | Validate and install one schema-preserving default |
| `Id::generate()` | `Result<Id, GenerateError>` | Use the cached default; do not wait for capacity |
| `Id::generator(node)` | `Result<Generator<Id>, GeneratorError>` | Validate expected node schema and share existing state |
| `generator.generate()` | `Result<Id, GenerateError>` | Same generation engine without global defaults |
| `Id::generate_blocking(timeout)` | `Result<Id, GenerateError>` | Retry transient capacity exhaustion with a time budget |
| `Id::generate_async().await` | `Result<Id, GenerateError>` | Optional Tokio capacity wait |
| `id.get()` | `Repr` | Return the stored integer |
| `TryFrom<i64>` / `TryFrom<u64>` | `Result<Id, InvalidId>` | Validate raw input without clock access |
| `From<Id> for Repr` | `Repr` | Lossless output |
| `FromStr` | `Result<Id, ParseIdError>` | Parse and apply the same raw validation |
| `id.parts()` | `Parts<Node>` | Decode without initialization |
| `Id::from_parts(parts)` | `Result<Id, InvalidId>` | Validate and encode, without reserving an ID |
| `id.unix_millis()` | `Result<u64, TimestampError>` | Checked epoch addition |

Generator handles also expose the same blocking and async waiting methods. Their
clone shares state. No public raw-state constructor or unchecked ID constructor
is part of this interface.

### Underlying traits

Two traits support the methods above without leaking registry or
state-management types:

```rust
pub trait Node: Copy + Send + Sync + 'static {
    /// `None` takes whatever node width the ID format declares.
    const BITS: Option<u8>;
    fn pack(self, bits: u8) -> Result<u64, NodeError>;
    fn unpack(raw: u64, bits: u8) -> Self;
}

pub trait Id: Copy + 'static {
    type Repr;
    type Node: Node;
    const FORMAT: Format;
}

pub fn init<N: Node>(node: N) -> Result<(), InitError>;
```

- `u32` implements `Node` with `BITS = None`. `TypedNode` implements it with
  `BITS = Some(n)`, and the ID declaration checks `n` against `FORMAT.bits.node`
  in a const context.
- `Id` is implemented only by `#[typedflake]`. Document it as not meant for manual
  implementation and keep engine hooks hidden. `Generator<I: Id>` and integration
  derives depend on this trait alone, so the derives never need to see the format.
- The global default stores the node's `TypeId` together with its packed value.
  Each ID type compares that against `TypeId::of::<Self::Node>()` when it first
  resolves its default generator.
- `pack` validates without truncation. `unpack` is infallible because a decoded
  node field always fits its declared width.

## 3. Behavior and guarantees

### Initialization

- Initialization is explicit and one-time; even node zero requires `init(0)`.
- Generating before initialization returns an error without freezing defaults.
- A second initialization returns `AlreadyInitialized`.
- Initialization validates the supplied node, but cannot enumerate every ID type
  in the program. Each generator also checks compatibility with its format.
- A `u32` node has no width of its own, so `init` can only reject it as already
  initialized; its range is checked per ID type when the default generator is
  resolved. `InitError`'s invalid-node case applies to typed nodes only.
- Tests that exercise `Id::generate()` call `let _ = typedflake::init(0);` and
  ignore `AlreadyInitialized`. Isolated tests prefer `Id::generator(node)`, which
  needs no global state. No test-only initialization API is provided.
- Schema mismatch and out-of-range defaults return errors, never delayed panics.
- Reading or parsing existing IDs does not require initialization.

### Clock and capacity

`generate()` returns immediately with an ID or an error rather than deliberately
sleeping for sequence capacity. This is not a wait-free latency guarantee: lazy
initialization and atomic contention still exist.

Keep errors typed and implement `Debug`, `Display`, and `std::error::Error`:

- `FormatError`: invalid widths or incompatible representation/node layout; used
  by pure validation and compile-time diagnostics.
- `NodeError`: invalid input fields, with field name, supplied value, and limit.
- `InitError`: invalid node or already initialized.
- `GeneratorError`: node/schema/format incompatibility during handle creation.
- `GenerateError`: missing defaults, default-generator configuration failure,
  clock read failure, clock before epoch, clock rollback, sequence exhaustion,
  timestamp exhaustion, or wait timeout.
- `InvalidId`: negative input, reserved bits, or out-of-range parts, including
  invalid node fields.
- `ParseIdError`: integer parsing failure or `InvalidId`, preserving its source.
- `TimestampError`: absolute timestamp arithmetic overflow.

Preserve lower-level errors as sources rather than flattening them into strings.
Error enums are `#[non_exhaustive]` and use named fields, for example
`NodeError { field, value, max }` and a rollback variant carrying how far the
clock is behind. The variants are the cases listed above; exact field sets must
be documented alongside implementation tests.

Start with a conservative policy: report clock rollback, fail permanently when
the timestamp no longer fits, and treat sequence exhaustion as retryable. Never
mask overflow or silently advance a logical clock.

A rollback error leaves the state untouched. Generation resumes on its own once
the clock reaches the last issued timestamp. Waiting entry points do not retry
rollback.

Optional waiting entry points:

```rust
let id = UserId::generate_blocking(Duration::from_millis(20))?;
let id = UserId::generate_async().await?; // Optional Tokio feature.
```

Blocking generation has a bounded wait. Async generation uses a Tokio timer only
when waiting is needed, supports normal cancellation/timeouts, and never calls
`thread::sleep` or spawns a blocking task for each ID. Both retry sequence
exhaustion only and reuse the same generation engine.
Measure the blocking wait budget using a monotonic clock, attempt once even for a
zero timeout, and return `WaitTimeout` if capacity remains unavailable. The budget
does not promise real-time scheduling or bound initial registry lock acquisition.
Async generation takes no timeout: capacity returns at the next millisecond, and
callers who need a bound wrap it in `tokio::time::timeout`.

### Uniqueness and ordering

- Uniqueness depends on exclusive node assignment within each identity domain.
- Different ID types may produce equal raw numbers; type safety is not a namespace
  encoded into the number.
- Processes using the same domain and node can collide.
- In-memory state alone cannot guarantee uniqueness across restarts and clock
  rollback. Deployment assumptions must be documented explicitly.
- Concurrent allocation order does not imply caller completion order.
- IDs from different nodes do not establish an exact global creation order.
- Changing epoch, bit allocation, or split-field meaning changes persisted format.

### Compatibility with existing IDs

This is a breaking release with a documented recipe, not an automatic migration.
Persisted IDs are never reinterpreted silently. The 0.2 default is `u64` with
42 timestamp, 5 worker, 5 process, and 12 sequence bits, epoch 2025-01-01, worker
above process. Two declarations read those IDs unchanged:

```rust
// Exact equivalent.
#[derive(Debug, Clone, Copy, TypedNode)]
pub struct LegacyNode {
    #[node(bits = 5)]
    pub worker: u8,
    #[node(bits = 5)]
    pub process: u8,
}

#[typedflake(
    epoch = "2025-01-01",
    bits(timestamp = 42, node = 10, sequence = 12),
    node = LegacyNode,
)]
pub struct UserId(u64);

// New default: same bit positions with the sign bit reserved.
#[typedflake(epoch = "2025-01-01")]
pub struct UserId(i64);
```

The `i64` form accepts existing IDs while bit 63 is zero, about 69.7 years from
the epoch. Its simple node equals `worker << 5 | process`. Users with a custom
legacy layout or epoch translate it by hand into a `Format` plus a typed node.
Pin this with fixed IDs generated by 0.2.0 that must decode identically.

## 4. Integrations

Cargo features make integration dependencies and derives available. Each ID opts
in using separate derives, never options inside `#[typedflake(...)]`:

```rust
#[typedflake(format = APP_IDS)]
#[derive(
    typedflake::Serde,
    typedflake::SqlxPostgres,
    typedflake::Postgres,
)]
pub struct UserId(i64);
```

| Derive | Cargo feature | Implementation target |
| --- | --- | --- |
| `typedflake::Serde` | `serde` | Serde `Serialize` and `Deserialize` |
| `typedflake::SqlxPostgres` | `sqlx-postgres` | SQLx PostgreSQL type and codecs |
| `typedflake::Postgres` | `postgres` | Shared `postgres-types` codecs |

The namespace is the prefix; do not add redundant `Id` or `TypedFlake` prefixes.
Keep SQLx's backend explicit. The `Postgres` derive is not Tokio-specific.
The optional `tokio` feature enables async generation independently of database
codecs. Enabling any feature must not silently implement integrations on other IDs.

### Serde

Serialize decimal strings and accept strings or integers on input. Route all
inputs through the same structural validation. Do not inspect global state or
the current time. Initially keep the representation stable across serializers
instead of implicitly switching string/numeric formats.

### SQLx

```rust
sqlx::query("INSERT INTO users (id, name) VALUES ($1, $2)")
    .bind(user_id)
    .bind(name)
    .execute(&pool)
    .await?;

#[derive(sqlx::FromRow)]
struct User {
    id: UserId,
    name: String,
}
```

Provide backend-specific `Type`, `Encode`, and `Decode` support. PostgreSQL array
support should be covered too. SQLx query macros may require their normal custom
type overrides; do not promise automatic inference from a `BIGINT` column.

Decode through the validated ID constructor. A transparent derive that simply
wraps any `i64` would bypass nonnegative and reserved-bit invariants. Serialization
and database decoding must reject the same invalid raw values as `TryFrom`.

### PostgreSQL clients

```rust
client.execute(
    "INSERT INTO users (id, name) VALUES ($1, $2)",
    &[&user_id, &name],
).await?;

let user_id: UserId = row.try_get("id")?;
```

Implement `postgres-types::ToSql` and `FromSql`, usable by both `tokio-postgres`
and the synchronous `postgres` client. Do not require a Tokio client dependency
just to implement its shared codecs.

Prioritize signed PostgreSQL storage. SQLite and MySQL mappings should be explicit
follow-up decisions. Full-width `u64` has no implicit PostgreSQL `BIGINT` mapping.
Initially restrict the PostgreSQL derives to `i64` IDs, including reduced-capacity
formats. Defer unsigned database adapters rather than add implicit signed storage.
Target SQLx 0.8, postgres-types 0.2, Serde 1, and Tokio 1 initially. The MSRV is
1.99, the toolchain the crate is built and tested with; older compilers are not
verified or promised.
Do not promise compatibility with multiple incompatible SQLx versions in one
integration feature.

## 5. Internal design and performance

Keep representation/codec logic independent from generation. Keep mutable state,
pools, atomic packing, and registry construction private. Provide only the traits
needed for real generic ID use and node declarations; do not expose the entire
engine as extension points.

The final workspace is two crates: `typedflake` for the runtime and public
interface, and `typedflake-macros` for declarations and diagnostics. The macros
do not need runtime logic at expansion time, so a separate core crate has no
consumer. New runtime code is written directly in `typedflake/src/`;
`typedflake-core` is deleted when the old interface is removed, without a
move-only step.

Require `std` and 64-bit atomics. Targets without `target_has_atomic = "64"` fail
with a clear `compile_error!` instead of a degraded fallback.

Implementation targets after initialization:

- One coordinated atomic timestamp/sequence state per ID type and node.
- No registry lookup or allocation on each generation call.
- No per-ID `Arc` cloning or intermediate string conversion.
- Cached default generator for the static entry point.
- Shared runtime logic rather than a full algorithm emitted for every ID.
- Correctness before memory-ordering or layout micro-optimizations.

Shared state lives for the rest of the process and is never evicted. The expected
cardinality is one node per ID type per process, not thousands of nodes.

Initialization may allocate and use locks. Do not describe the entire library as
lock-free. Benchmark static and explicit generation, contention, initialization,
sequence rollover, and integration codecs separately.

Use an internal clock seam for deterministic tests. A public clock abstraction is
not required unless a real supported use case needs it.

**Selected** records defaults chosen under the delegated design decisions.

accepted declaration syntax; they concern implementation and release planning.

The split field order is part of the wire format, not merely a source refactor.
Runtime schema identity is not a portable cross-process format identifier. Decide
whether format fingerprints are useful later; they are not needed for the first
interface draft.
